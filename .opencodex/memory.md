## AI-слой (единый YandexGPT-клиент + Yandex Vision OCR, чистый)
- `internal/ai/yandexgpt/client.go`: `Client`, `NewClient(cfg Config)`. Конфигурация (ключ/каталог/модель/лимит) — ТОЛЬКО из `config.Config`. `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, `YANDEX_MODEL` (дефолт `yandexgpt.DefaultModel`), `YANDEX_MAX_CONCURRENCY` (дефолт `DefaultMaxConcurrency`=4). Пустой ключ → `NewClient` ОК, вызовы возвращают `ErrYandexKeyNotSet`. НЕТ прокси.
- **ПРОМПТЫ И ВСЕ ТЕКСТЫ — В LOCALES:** системные промпты и пользовательские в `internal/locales/prompts*.go`; ошибки в `errors.go`, логи в `logs.go`. Хардкода текстов/промптов в client.go НЕТ.
- **СИСТЕМНЫЙ ПРОМПТ КОНСУЛЬТАЦИИ (`SystemPromptMedicalAnalyst`):** ИИ = «опытный врач-терапевт, который ПОМОГАЕТ отвечать»; НЕ отказывается; диагноз НЕ ставит; в конце ОБЯЗАТЕЛЬНО дисклеймер «это не является диагнозом, а лишь информационные рекомендации; при ухудшении состояния нужно обратиться к врачу». ⚠️ Отказы вида «Я не могу обсуждать эту тему» возвращает САМА модель YandexGPT (встроенный safety), а НЕ код — промпт лишь снижает вероятность. Пользовательский промпт консультации — `consultationTextPrompt` в `router_menu_actions.go` (дублирует этот дисклеймер).
- **VISION (мультимодальный) — СТАНДАРТ для «живых» фото (фигура/травма).** YandexGPT текстовая, но умеет принимать изображения в `messages[].images` (base64, БЕЗ data-URI). Метод `generateMultimodal(ctx, systemPrompt, userPrompt, images, maxTokens, temp)` + хелпер `visionImages([][]byte)` (пропускает пустые и >`maxVisionImageBytes`=5 МБ). Vision-пути с фолбэком на OCR+текст реализованы для: базовый Bioscan (`GenerateBioscanJSON` → `PromptForBioscanBasicVision` + `SystemPromptBioscanVision`), Bioscan PRO (`GenerateBodyScanJSON` → `PromptForBodyScanVision` + `SystemPromptBodyIntelligenceVision`, анализирует 4 ракурса), консультация по фото (`GenerateAnalysisFromFileVision` → `PromptForAnalysisVision` + `SystemPromptAnalysis`, сервис `HandleConsultationImage`). ⚠️ Документы (анализы крови/скриншоты бланков) НЕ через vision, а через OCR (`recognizeText`) — иначе модель «не прочитает» таблицу; vision только для «живых» снимков тела/травмы. Промпты vision собираются КОНКАТЕНАЦИЕЙ (не `fmt.Sprintf`), т.к. содержат литеральные `%`.
- Обычные текстовые/doc-методы (OCR): 9 методов AIClient (см. интерфейс `service.AnalysisService` / `client.go`).
- `generateText(ctx, systemPrompt, userPrompt, maxTokens, temperature)` — completion-вызов. Таймаут `DefaultTimeout`=120с.
- **AI-СЕМАФОР:** `Client.sem = semaphore.NewWeighted(cfg.MaxConcurrency)`; `sem.Acquire/Release` в `generateText`/`generateMultimodal`.
- **НАДЁЖНОСТЬ:** `doRequestWithRetry` повторяет `defaultMaxRetries=3` раза с экспоненциальным backoff (старт `defaultRetryBackoff=400ms`, x2) на сетевую ошибку и HTTP 429/5xx; 2xx и 4xx (кроме 429) НЕ повторяются; backoff уважает `ctx.Done()`. OCR-адаптер повторяет с теми же правилами.
- **OCR-МАРШРУТИЗАЦИЯ ПО ТИПУ ФАЙЛА (важно для правки OCR):** изображения (`image/*`) идут в Yandex Vision OCR `recognizeText` (`ocr.api.cloud.yandex.net/ocr/v1/recognizeText`); PDF (`application/pdf`) — в Yandex **Vision API** `batchAnalyze`+`TEXT_DETECTION` (`vision.api.cloud.yandex.net/vision/v1/batchAnalyze`). Причина: `recognizeText` PDF НЕ принимает (ошибка "Can't decode image"), а путь `/recognize` на OCR-эндпоинте НЕ существует (404). Публичный `recognizeText(ctx,data,mimeType)` диспетчеризует по MIME: PDF→`recognizeDocument`→`doVisionOCROnce`→`extractVisionOCRText` (results[].results[].text_detection.pages[].blocks[].lines[].words[].text); изображения→`recognizeImage`→`doImageOCROnce`→`extractOCRText` (result.textAnnotation.fullText). Тесты (`client_test.go`) мокают `visionEndpoint` для PDF и `ocrEndpoint` для изображений.

## Слой БД (SQLite ⇄ Yandex Cloud PostgreSQL)
- Бот **драйвер-агностичен**: код пишется в стиле SQLite (`?`-плейсхолдеры), репозитории оборачивают запросы через `db.BindQuery(driver, q)` (`?`→`$N` только для `driver=="postgres"`). `db.Migrate(conn, driver...)` диалект-зависим: postgres — `BIGSERIAL`+`TIMESTAMP`, sqlite — `AUTOINCREMENT`+`DATETIME`. `db.OpenConfig(cfg)` + `config.DB_DRIVER`. При старте бот САМ накатывает схему (`db.Migrate` с driver=postgres создаёт все таблицы). `ensureNotificationSchema` ветвится по driver.
- **PostgreSQL-специфика (скрыта за ветками driver=="postgres"):** `RETURNING id` вместо `LastInsertId()` (SaveDiagnosis/CreateCycle/SaveResult/CreateProject); `ON CONFLICT DO NOTHING` вместо `INSERT OR IGNORE` (BindEntry, recordSubscriptionNotification); `end_date IS NULL` без сравнения с `''` (GetActiveCycleByUserID).
- Пул для PG: `SetMaxOpenConns(12)/SetMaxIdleConns(4)/SetConnMaxLifetime(30m)`.
- Деливераблы миграции (уже есть): `migrations/schema_postgres.sql` (эталон DDL), `migrations/migrate_sqlite_to_pg.load` (pgloader: SQLite→PG, править host/user/пароль-`CHANGE_ME` и путь к CA), `cmd/dbcheck` (`go run ./cmd/dbcheck` — пингует БД из окружения бота и делает SELECT 1). Перенос данных из SQLite в PG — через pgloader по `migrate_sqlite_to_pg.load` (нужно поставить pgloader и отредактировать креды/CA).
- ⚠️ **БАГ БАЗОВОГОС BIOSCAN — ИСПРАВЛЕН (аудит):** базовый и PRO Bioscan хранятся с `type="bioscan"` — это ок. Реальный корень путаницы: бэкенд НЕ выставлял поле `rich` у `ReportBlock`, а фронт (`dashboard/webapp_files/app.js`) по `latest.rich` выбирает подпись карточки («✨ Bioscan PRO» vs «✨ Базовый Bioscan»). Фикс: в `dashboard/reports_data.go` добавлено поле `Rich bool` в `ReportBlock` и оно вычисляется в `parseReportBlock` по наличию структуры (MainScore>0 / Scores / Indicators / Zones). Базовый Bioscan (JSON `{"title","note"}`, без score/zones) → `Rich=false` → подпись «Базовый Bioscan», не загрязняет PRO-секцию; Bioscan PRO/досье → `Rich=true`. Дополнительно `parseBioscanBlock` сохраняет `note`→`Summary`. Тест: `TestParseReportBlockRich`. БАГ2 (UX) — ИСПРАВЛЕН: в `router.go` блоки `StateWaitingConsultation`/`StateWaitingFeedback` при нажатии кнопки главного меню теперь делают `SetState(Idle)` И сразу вызывают `handleMenuButtons` (с `return`), так что меню навигирует с первого нажатия, без «второго клика».

## Готчи при правке
- ⚠️ `internal/locales/messages.go` может быть ПОВРЕЖДЁН в рабочем дереве (обрезанный литерал) → `git checkout -- internal/locales/messages.go`.
- ⚠️ Демо-правки `dashboard.go` живут ТОЛЬКО в рабочем дереве — **НЕ `git checkout -- internal/bot/handlers/dashboard/dashboard.go`**.
- ⚠️ `internal/db/db.go` `Migrate` использует WAL + `busy_timeout(5000)` + `synchronous(NORMAL)`; пул `SetMaxOpenConns(8)`/`SetMaxIdleConns(8)`. В миграциях `conn.Query(...)` БЕЗ `rows.Close()` → утечка соединения. Либо `QueryRow().Scan()`, либо `rows.Close()`.
- ⚠️ В Go inline-кнопки/клавиатуры: каждая кнопка — `models.InlineKeyboardButton{...}` внутри среза-строки, поэтому в литерале `{{...}}` (двойные фигурные скобки), иначе компилятор ругается.
- ⚠️ `WebAppAssetsVersion`/`WithWebAppVersion`/`OpenHealthSummaryButton` — в пакете `keyboards`.
- ⚠️ **РАССИНХРОН ВЕРСИЙ ФРОНТА = СТАРЫЙ КЭШ В Telegram:** `WebAppAssetsVersion` (Go, `keyboards/webapp.go`) и ссылки `style.<ver>.css`/`app.<ver>.js` в `webapp_files/index.html` ДОЛЖНЫ совпадать. `ServeWebApp` отдаёт актуальный встроенный файл для ЛЮБОЙ версии (резолвит `app.<ver>.js`→`app.js`), поэтому контент правильный вне зависимости от цифры — НО браузер/WebView Telegram кэширует JS/CSS ПО URL, часто игнорируя `no-store`. Если Go=v58, а index.html грузит v57 (устаревший URL), клиент получает ЗАКЭШИРОВАННЫЙ старый фронт (старые скобки/точки в профиле, старые табы). Лечение: поднять ссылки в `index.html` до той же версии, что и Go (новый URL → чистый кэш). Правишь фронт — поднимай ВЕРСИЮ синхронно В ОБОИХ местах.

## Напоминания (internal/bot/reminders)
- `RunReminderLoop` (goroutine в app.Run, раз в 6ч) по `users.last_activity_date`: ≥10 дней неактивности → `GetRandomReminder()` из `locales.Reminders` (≤200 символов); ставит `last_activity_date=now`. Уважает `Preferences.NotificationsEnabled`. `BroadcastFeature` — одноразовая рассылка.
- **Единый флаг `Preferences.NotificationsEnabled` (def=on)** управляет ВСЕМИ уведомлениями. Переключается: бот-команда `/notifications on|off|status`; из «Мой профиль» через `GET/POST /api/notifications` (`dashboard.Handler.Notifications` + карточка в `webapp_files/app.js`; `notifSvc` проброшен в `dashboard.NewHandler`). GET при отсутствии строки предпочтений дефолтно `enabled=true`; POST `{"action":"off"|"on"}`. Демо `?demo=1` — синтетика без БД.
